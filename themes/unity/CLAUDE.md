# CLAUDE.md

A standalone Hugo theme that renders a personal site as the Ubuntu 14.04 Unity desktop. Hugo partials server-render everything, `assets/unity/css/main.css` styles it, and the TypeScript modules under `assets/unity/js/` enhance the rendered DOM. Hugo Pipes bundles the TypeScript at site build time, so this directory has no build step of its own. README.md documents the surface a consuming site configures.

## Constraints

- A bare site with no params, menu, or data files must keep building. Guard every optional read. `npm run test:sites` builds `exampleSite/` and small sites of other shapes with warnings fatal, then checks their output. Its link check fails on any link to a file that a site's build lacks, absolute URLs on the site's own host included, so fixture data that links an outside page must use another host. The example site must use every template. Add a site to `scripts/build-sites.ts` when a fix covers a site shape the others miss.
- The `misconfigured` site in `scripts/build-sites.ts` triggers each warning that a site's config, data, or front matter can cause. It checks that the build still succeeds and falls back to the default that each mistake replaces. Add a pattern to it for each new `warnf` that does not depend on the network.
- `hugo.toml` sets `markup` and `taxonomies`, but Hugo merges them only into a site that sets `_merge = "deep"` on its own table. The example site opts in, and the other test sites do not. Templates must still build on a site that keeps Hugo's defaults, where highlighted code carries style attributes and the site does not declare a `series` taxonomy.
- Every asset the theme owns lives under `assets/unity/`, so a site's own `assets/css/main.css` or `assets/icons/` never replaces one. Keep new assets there. `assets/css/custom.css` is the one path the theme reads outside it, because it is the site's hook. The `clash` site in `scripts/build-sites.ts` checks that a site's own assets leave the theme's in place.
- A site needs only Hugo, in either edition. Do not add anything that needs Node, npm, Dart Sass, or the extended edition at site build time.
- `package.hugo.json` does not declare any packages. Hugo's `hugo mod npm pack` reads it in place of `package.json`, so the theme's dev tooling never reaches a site's npm workspace. Hugo also hashes it in place of `package.json` to decide whether a site's packed dependencies are stale, so Hugo never warns a site about an edit to `package.json`. Do not edit `package.hugo.json`, because every edit makes Hugo warn each site that has run the pack. The `npmpack` site in `scripts/build-sites.ts` checks that the pack gets nothing from the theme.
- Two builds of the same site write identical files, and the `example` site in `scripts/build-sites.ts` builds twice to check it. Never render a `math.Counter` value, because its order changes with Hugo's concurrent rendering. Never render the build's time of day either. Render such a value empty and let a script fill it, as the clock indicator does.
- Hugo reads the version floor from `module.hugoVersion.min` in `hugo.toml`. The `$floor` guard at the top of `baseof.html` and the requirements in README.md repeat it, and the `example` site in `scripts/build-sites.ts` checks that they match. Change the `theme-floor` CI job of the site that hosts the theme whenever the floor changes. Keep the floor out of `theme.toml`, because Hugo ignores its `min_version` when `hugo.toml` sets one.
- All desktop state is session-only by design. Only the terminal's command history persists.
- `main.css` is one file on purpose, so do not split it. It is plain CSS with native nesting, and `css.Build` in `_partials/unity/head/css.html` lowers the nesting for the browser targets listed there. That build puts `main.css` in the `unity.theme` cascade layer and the highlighter's classes in the later `unity.chroma` layer. Every unlayered style beats a layered rule whatever its specificity, so a site's `custom.css` overrides `main.css`, and so do the style elements xterm.js adds at runtime. A `!important` in `main.css` beats every site rule, even a site's own `!important`, so add one only where no site has a reason to override it. Every selector is prefixed `up-`. Every custom property is prefixed `--up-`, including the ones the scripts set with `style.setProperty`. The accent tokens are `--up-accent` and its `-light`, `-dark`, and `-darker` shades. Every rule names its font family through `--up-font-sans` or `--up-font-mono`, and every script that draws text reads the mono stack through `monoFamily()` in `fonts.ts`. `fonts.test.ts` fails on any other family outside the `@font-face` blocks, the vendored xterm block, and MathML.
- The `css.Build` targets in `_partials/unity/head/css.html` are the theme's browser floor, and the Requirements in README.md name them, so change both together. `browser-targets.test.ts` fails when a target lacks a feature that `css.Build` leaves as written, such as `:has()`, or when README.md does not name a target's version.
- The first `:root` block in `main.css` holds the tokens that a site sets in `custom.css`. The table under Customizing in README.md lists each one, so change both together. A rule that paints a token's role reads the token instead of repeating its value. `tokens.test.ts` fails when the table and the block differ, or when a rule repeats a token's value outside the exceptions the test lists. It also fails when no rule or script reads a custom property that `main.css` declares, and when a rule reads one that nothing declares or sets.
- `main.css` has no mixins, so shared looks repeat inline after a `/* recipe: <name> */` marker. Grep the marker and change every copy together. Every recipe with more than two copies reads its colors, gradients, and shadows from internal tokens, so one token edit changes every copy. The copies repeat only structure, such as radii and padding. The recipe tokens have their own `:root` block, apart from the tokens a site sets, and the Studio's sit with the other `--up-daw-*` tokens on `.up-daw-body`. `tokens.test.ts` fails when a rule repeats an internal token's gradient or shadow.
- Every dark surface that scrolls or holds a form control declares `color-scheme:dark` in its own rule, so the browser draws its scrollbars and controls dark. Prose code blocks do not declare it, because the site's highlight style might paint them light. `color-scheme.test.ts` fails when a rule scrolls over a dark background without the declaration, outside the exceptions the test lists. It also fails when a rule declares another scheme or declares the dark one over a light background.
- Every focus ring keeps a contrast of at least 3:1 with the surface under it. A ring on a light surface paints `--up-accent`, and a ring on a dark surface paints `--up-accent-light`. A selected row or tile fills with the accent, so its ring paints white. Every control that `all:unset` strips of the browser's ring draws its own. `focus-ring.test.ts` fails when an accent ring is not 2px solid, when a ring over an accent fill reads an accent token, or when a ring on a light surface reads another shade. It also fails when an `all:unset` control draws no ring on focus, when a preset's `light` contrasts less than 3:1 with white, or when its `color` contrasts less than 3:1 with a light surface.
- Under forced colors, such as a Windows contrast theme, the browser replaces every color with a system color and drops every shadow and gradient. The `@media (forced-colors: active)` block at the end of `main.css` restores the cues that forced colors removes. Focus states that draw no outline get a CanvasText ring there. Selected, current, and pressed states fill with Highlight there and opt out of forced colors with `forced-color-adjust:none`, so each fill and every rule inside it name their colors. `forced-colors.test.ts` fails when a focus state removes the outline without drawing one back, or when a state rule sets only colors and the block has no rule for its selector. It also fails when the block names a color other than a system color.
- Live white text on a dark surface is at least half opaque, so it contrasts 4.5:1 or more with the surface. Highlights that fill with `--up-accent` or `--up-accent-light` behind white text contrast less than 4.5:1 with it for some presets, and the theme keeps them for the brand look. When the visitor's system asks for more contrast, the `@media (prefers-contrast: more)` block fills each of them with `--up-accent-dark` instead. That block sits before the forced-colors block, so forced colors win on a system that asks for both. `contrast.test.ts` fails when a highlight has no rule in the block, when white text on a fill there contrasts less than 4.5:1 for any preset, or when the block follows the forced-colors block. It also fails when live white text is less than half opaque outside the exceptions the test lists, or when an alert's title contrasts less than 4.5:1 with its bar.
- The titlebar beads, each window's close, minimize, and maximize buttons, draw at 14px. Each bead's `::after` widens its hit area to a 24px square, the WCAG 2.2 minimum target size. The beads sit 24px apart center to center, so their hit areas never overlap, and they stack above the resize zones that `resize.ts` adds. `target-size.test.ts` fails when a hit area is smaller than 24px, reaches past the titlebar, or overlaps another, or when the beads stack below the resize zones. It also fails when the title's end margin stops matching the width of a three-bead group. The dialog's close button stands alone in its titlebar, so WCAG's spacing exception covers its 14px target, but a second button there must get the same hit area.
- `baseof.html` sets `dir` on `<html>` from the language's `direction`. The top panel, its menus, and everything inside a window use logical properties, such as `margin-inline-start`, `border-inline-end`, and `text-align:start`, so they mirror on a right-to-left page. Each dropdown's `data-align` names the edge it shares with its trigger, `start` or `end`. The launcher stays on the left edge in every language. The surfaces placed against it keep physical properties: the launcher, the window stages, the Dash, the HUD, the notification bubbles, the desktop label, and the resize zones. A mirror that no logical property expresses, such as a directional glyph, an inset highlight, or a transform, gets a `[dir="rtl"]` rule nested in its rule, because the browser floor predates `:dir()`. The Studio's body carries `dir="ltr"`, like the xterm.js terminal, because its piano roll runs left to right in every language. `direction.test.ts` fails on a physical left or right outside the surfaces it lists, and on a back, forward, or side-pointing glyph whose element has no mirror rule. The `rtl` site in `scripts/build-sites.ts` checks that a right-to-left language's pages set `dir="rtl"`.
- Reduce motion is the `up-reduce-motion` class on `<body>`, which Edit > Preferences toggles. `followSystemMotion()` in `prefs.ts` sets the class from the visitor's system setting when `app.ts` starts and again each time the setting changes. The reduce-motion rules in `main.css` stop every animation and transition, but they cannot reach a smooth scroll or a `requestAnimationFrame` loop that a script starts. So every script checks the class through `isReduceMotion()` in `prefs.ts` before it starts such motion, and every scroll takes its behavior from `scrollBehavior()` there. A window that follows the pointer during a drag keeps moving, because the visitor drives that motion. `reduced-motion.test.ts` fails when a script outside `prefs.ts` reads the system setting or names a smooth scroll, or when the page window springs home under reduce motion.
- Every string a template renders goes through `partial "unity/ui/t" "<key>"`, or `partial "unity/ui/t" (slice "<key>" <arg>)` where Hugo's `T` takes an argument, with the English in `i18n/en.toml`. `_partials/unity/ui/t.html` calls `T` and fills a key the site's translation lacks from the theme's English, so never call `T` directly. Templates pass each key as a string literal, except that a `printf` format such as `alert_%s` stands for every key that starts with its literal text. `i18n.test.ts` checks that every key the templates use exists and that they use every key in `en.toml` outside the `js_` keys.
- Keys hold whole sentences, with a placeholder for each value, so each translation sets its own word order and punctuation. Each placeholder takes a name, a number, or a counted phrase such as `{n} moves`, never a translated word whose form depends on the sentence around it. Never join a translated fragment to other text or change the case of translated text. Scripts join each list of values through `Intl.ListFormat` with `locale()` from `i18n.ts`, so every list follows the page's language.
- When a value renders as markup, such as the cv page's page number box, the template passes a control character in its place. `_partials/unity/ui/slots.html` splits the sentence around that character, and the template renders the markup in its slot. The `sentences` site in `scripts/build-sites.ts` checks that each piece of markup lands where a translation puts its placeholder.
- Every string the desktop's scripts show goes through `t("js_<key>")` or `tn()` from `assets/unity/js/i18n.ts`, with the English under the `js_` keys at the end of `en.toml`. `_partials/unity/ui/i18n.html` renders those keys for the page's language. `npm run i18n:types` generates `assets/unity/js/i18n-keys.ts` from `en.toml`, so adding, renaming, or removing a `js_` key or a placeholder means editing `en.toml` and running the generator. That file types each key and the placeholders that its string fills. tsc then fails on a key that `en.toml` lacks and on a call that misses or misspells a placeholder. `i18n.test.ts` fails while the committed file differs from the generator's output. It also finds each key that a script uses by its string literal, so it fails on a key that is not a literal and on a `js_` key that no script uses. The home terminal's output stays English, like the bash it imitates.
- A consuming site needs no npm. xterm.js and pdf.js are vendored under `assets/unity/third_party/`, never a directory named `vendor`, because Go module zips drop `vendor` directories and a site importing the theme as a Hugo module would lose them, and `_partials/unity/ui/script.html` shims the `@xterm/*` and `pdfjs-dist` imports to those files. `npm run vendor:xterm` and `npm run vendor:pdfjs` refresh them from the versions in `scripts/`. esbuild keeps only legal comments in a bundle, so `vendor-pdfjs.ts` opens pdf.js's licence header with `/*!`, and the `example` site in `scripts/build-sites.ts` checks that each bundle that inlines a vendored library keeps the library's notice. pdf.js ships no type declarations, so `assets/unity/js/pdfjs.d.ts` declares the slice `cv.ts` uses. `npm run typecheck` checks that file and the vendored xterm declarations, so keep `skipLibCheck` off in `tsconfig.json`. The structural CSS from `@xterm/xterm` is inlined in `main.css` under a version pin, so bump it with the vendored copy.

## Layouts

- Every partial the theme owns lives under `_partials/unity/`, so a site's own `_partials/author.html` or `_partials/head.html` never replaces one. Keep new partials there and call them by that path, such as `partial "unity/icon.html"`. The `extend-*` hooks are the only partials outside it, because they are the site's hooks. The `clash` site in `scripts/build-sites.ts` checks that a site's own partials leave the theme's in place.
- `baseof.html` is the only base template. It wraps `{{ block "main" }}` in the page window, so a layout's `main` block emits inner content only and never its own outer wrapper or titlebar.
- The desktop chrome repeats on every page. The top panel, the launcher, and the partials that `baseof.html` marks render their page-independent parts through `partialCached`, once per language. `top-panel.html` and `launcher.html` render only their page-dependent parts per page, and the launcher's dock renders once per set of current tiles. Each cached partial says so in its header and must never read the page. A partial that starts to read the page must switch its callers to `partial`, or pass what it reads as a `partialCached` variant.
- Templates never name the blog section or its taxonomies. `_partials/unity/blog-section.html` resolves the section from `mainSections`, `_partials/unity/in-blog.html` is the "is this a post" test, and `_partials/unity/blog-posts.html` lists the posts. Never test `in site.MainSections .Section` directly, because Hugo sets `mainSections` to `[""]` on a site without sections. `_partials/unity/blog-taxonomies.html` names the category and series taxonomies, and `_partials/unity/post-categories.html` reads a post's categories.
- Bespoke pages select `layouts/<layout>.html` through `layout` front matter, and each one renders `_partials/unity/page/<layout>.html`. Adding a page means adding both files and documenting the front matter the partial reads in its header comment.
- `_partials/unity/page-title.html` names a page wherever a template shows its title. Hugo leaves `.Title` empty on a page without title front matter and on the home page of a site without a title. It also titles the 404 page in English. Render a page's title through this partial, never through `.Title`. `npm run test:sites` fails on an empty title in any page or feed of any site.
- `_partials/unity/window-title.html` titles the page window and the top panel. The home terminal's window reads like a terminal's, `user@host: ~`, unless the home sets a title. Every other window shows the page title. Read the terminal's guest login through `_partials/unity/terminal-login.html`.
- The shell's prompt retitles the terminal's window after each change of directory, such as `user@host: ~/posts`. Like PS1 in Ubuntu's `.bashrc`, it writes an OSC title sequence, which `TerminalIO` reports through `onTitleChange`. The shell bundle sends each title as the `up:page-window-title` event, and the app bundle writes it to the titlebar and the top panel. The island's `cwdTitle` turns the sequence on only when the window shows the login's title, so a home's own title stays.
- `_partials/unity/author.html` normalizes `params.author`, which a site may set as a table or a plain name, so read the owner through it. `_partials/unity/socials.html` does the same for `params.social`, and `_partials/unity/projects-data.html` fills in each project's optional keys. These normalizers parse every date a site writes through `_partials/unity/ui/iso-date.html`. They warn when a set value comes back empty, so a typo names its param instead of failing the build. Other templates read the normalized YYYY-MM-DD and never call `time.AsTime` on a site's value.
- `_partials/unity/site-pages.html` is the page registry built from `menu.main`. The launcher, Dash, HUD, File menu, and `nav:<key>` actions all read it. An entry with neither a page nor a url drops out with a warning. A link to the home page in its place would match every page under the default prefix match, so its tile would be current everywhere.
- Resolve every menu entry's address through `_partials/unity/menu-url.html`, so the theme's menus agree on what `pageRef` and `url` mean. The Help menu reads `menu.help` this way. The partial reads a url entry's raw `.MenuConfig.URL`, because Hugo's `.URL` mangles a root-relative url. It returns an empty string for an entry with neither a page nor a url, and every caller leaves such an entry out.
- Never render a URL from front matter, data, or config as written, because a root-relative path breaks on a site served from a subdirectory. Resolve it through `_partials/unity/ui/resolve-url.html`, which works the way the Markdown render hooks do, or through `_partials/unity/markup/site-url.html` for a path under `baseURL`. The `urls` site in `scripts/build-sites.ts` checks the menu and the sponsors page.
- `_partials/unity/projects-data.html` resolves the projects from `data/projects` or, without it, the GitHub API. The projects page and the Dash read projects only through it.
- `_partials/unity/lang-indicator.html` renders nothing on a monolingual site, so a bare site's panel stays unchanged.
- `_partials/unity/top-panel.html` renders the indicators that `params.desktop.indicators` names, in order, each from `_partials/unity/indicators/<name>.html` through `partialCached` with the site as context. Sites add indicators of their own there, so the panel scripts must tolerate a missing indicator and an extra one. The language badge stays outside the list.
- Every line that imitates the shell, such as a prompt from `_partials/unity/ui/term-prompt.html`, sits in an element with `dir="ltr"`, so it reads left to right on a right-to-left page. The home terminal's mount also sets `lang="en"`. Every name from the site that the desktop's chrome shows sits in an element with `dir="auto"`, so it takes the direction of its first letter, like a GTK label. Such names include page titles in the titlebar, pathbar, post list, and Dash, tag chips, and project names. The `rtl` site in `scripts/build-sites.ts` checks both.
- `_partials/unity/playlist.html` resolves the Studio's MIDI files from the site. An empty playlist removes every Studio surface, so gate any new one on it.
- `baseof.html` builds the app bundle with the esbuild define `UP_STUDIO` set to whether the playlist has tracks, and publishes the Studio's variant as `js/app-studio.js`. esbuild then drops the Studio's code from a site without MIDI files. Every call into `daw.ts` or `audio.ts` from another module goes inside an `if (UP_STUDIO)` block or after `UP_STUDIO &&`. Never guard one with an early `if (!UP_STUDIO) return`, because esbuild keeps the modules that the code after a return names. esbuild also keeps a module's top-level calls and object spreads even when nothing reads their results. Keep both off the top level of `daw.ts` and `audio.ts`. Build a table that calls `t()` inside the function that reads it, as `initDaw()` does. The `bare` site in `scripts/build-sites.ts` fails when `js/app.js` carries a Studio label key.
- The accent presets live under `params.desktop.accents` in `hugo.toml`, and `_partials/unity/accents.html` resolves them together with a site's own. `_partials/unity/head/css.html` builds each preset's rule from that partial, `_partials/unity/ui/runtime.html` publishes the names and labels that `prefs.ts` draws as swatches, and `baseof.html` names the starting preset in `data-up-accent` on `<html>`. Each built-in preset takes its label from its `accent_<name>` key in `i18n/en.toml`, so add the key with the preset. The internal accent block in `main.css` repeats the `orange` shades for a site that removes every preset, so change both together. `tokens.test.ts` fails when they differ. The `accents` site in `scripts/build-sites.ts` checks the merge and the order, and the `misconfigured` site checks each preset warning and the fallback.
- Every bundle except the app's loads only on the pages that render its root element. The template that renders a root names its bundle with `.Store.SetInMap "unity-bundles" "<name>" "<entry>"`. After `block "main"` renders, `baseof.html` ships each bundle in that store as `js/<name>.js`, so a site's own layout can render a page partial under any name. Never call a partial that names a bundle through `partialCached`, because a cached call skips the store on every page after the first. `hugo server` keeps a page's store when only a template changes, so a bundle that a template stops naming keeps loading until the server restarts.
- `_partials/unity/icon.html` inlines an icon from `assets/unity/icons/`, and `_partials/unity/icon-img.html` renders one as an `<img>` of a published copy. Render the full-color art that the chrome repeats on every page through `icon-img.html`, so the browser caches it and each page's HTML stays small. `icon-img.html` inlines an icon that paints with `currentColor`, because only an inline copy inherits the page's color.
- `rss.xml` renders every feed. The home feed lists the blog's posts only, so utility pages never surface as entries.
- The render hooks under `_markup/` own Markdown output. A hook whose markup a feed reader cannot use has a `.rss.xml` twin, and the link and image hooks share their resolution with their twins through `_partials/unity/markup/`. Change a hook and its twin together.
- `_shortcodes/youtube.html` replaces Hugo's embedded youtube shortcode, because Hugo's sizes the player with style attributes. It copies Hugo's template with the changes its header lists. Keep its arguments and `privacy.youtube` handling the same as Hugo's, and diff the two when Hugo changes its copy. The `youtube` site in `scripts/build-sites.ts` checks it.
- `_partials/unity/head/meta.html` renders all search and share metadata. The theme does not call Hugo's embedded `opengraph.html` or `twitter_cards.html`, because they describe the home page by its body, which is the terminal's README.
- `_partials/unity/head.html` renders `_partials/extend-head.html` last, and `_partials/unity/head/css.html` builds the site's `assets/css/custom.css` into the stylesheet after the theme's layers, with no layer of its own. `baseof.html` renders `_partials/extend-footer.html` before `</body>`, and `_partials/unity/page/post-reader.html` renders `_partials/extend-post.html` after a post's body. The hook partials ship empty and are the documented override points, so keep them. The `hooks` site in `scripts/build-sites.ts` checks that each hook, `custom.css` included, lands where README.md says.

## DOM contracts

TypeScript types the JavaScript surface but not the DOM. Each module selects its root by a `data-*` attribute and no-ops when the attribute is absent. Renaming any `data-*` attribute or `up-` class a module reads breaks it silently, and so does renaming any `--up-` custom property a module sets. Grep `assets/unity/js/` before renaming anything in a partial or in `main.css`. The larger partials list the attributes their module reads in a header comment. The HUD indexes the top panel's rendered menus as its search index, so that markup is a contract too.

`dom-contract.test.ts` fails when a script reads a `data-*` attribute or `up-` class that no template, icon, or script writes. It reads names only from literal text, so spell each name out in full. A script passes each `data-*` name it writes straight to `setAttribute` or `toggleAttribute`, because the test counts any other `data-*` name as one the script reads. The panel's battery, volume, play, and pause glyphs under `assets/unity/icons/glyphs/` carry `data-*` attributes that `top-panel.ts` reads.

A module that needs several nodes passes their lookups to `requireAll()` in `dom.ts` and returns when it yields null. It destructures the result into consts, which keep their non-null types inside function declarations, so the module never asserts a lookup with `!`.

The top panel's File, Edit, View, and Help menus follow the WAI-ARIA menu button pattern. `_partials/unity/ui/panel-menu.html` gives each dropdown body `role="menu"`, and `_partials/unity/ui/menu-item.html` gives each row a menu item role with its checked and disabled states. The indicators follow the disclosure pattern instead, because their dropdowns hold sliders, calendars, and buttons that a menu cannot contain. Their triggers name the dropdown through `aria-controls` and never set `aria-haspopup`. The `example` site in `scripts/build-sites.ts` checks both patterns on every page.

`panelKey()` in `panel-keys.ts` maps each key in the top panel to what it does, and `panel-keys.test.ts` checks the map. Every menu row carries `tabindex="-1"`, so Tab closes a menu and moves on from its trigger. Each indicator's dropdown keeps Tab for its controls, and the panel closes the dropdown when focus moves out of it.

Left and Right follow the inline direction in the panel's triggers, the Dash's tiles, the projects grid, and every other row of controls they step through. On a right-to-left page, Left moves to the next control. `inlineStep()` in `inline-keys.ts` maps each key to a step in document order, and `inlineDirection()` reads the computed direction of the element that lays out the row. The solitaire cursor keeps physical arrows, because its canvas draws the same table in every direction.

`_partials/unity/ui/runtime.html` publishes `window.UP_SITE` and `window.UP_I18N` in a per-language script that loads before the bundles. The theme renders no inline script, event handler, style element, or style attribute, so it runs under a Content Security Policy without `'unsafe-inline'`. Keep it that way. The example site's checks in `scripts/build-sites.ts` fail on any inline script, event handler, or style, and `npm run test:browser` fails on each one that Chromium blocks. Put the styles of a no-JavaScript fallback in `main.css` under `@media (scripting: none)`.

Pass page data in a `<script type="application/json">` block like the home terminal's. Read such a block through a parser that checks each field, like `parseShellIsland()` in `shell/island.ts` for the home terminal's island, never through a cast. The `Window` augmentation in `assets/unity/js/types.ts` must match `UP_SITE` and `UP_I18N`. `contracts.test.ts` builds the example site and a bare site with Hugo, then checks the island and both globals against their types. It skips when Hugo is not on PATH.

## Cross-bundle contracts

The app, projects, and shell bundles are separate IIFEs and cannot import each other at runtime.

- The bundles talk through window and document events. `events.ts` names each event and declares its detail type in `UPWindowEvents` or `UPDocumentEvents`, and it derives the DOM event maps from those interfaces. It has no side effects, so every bundle imports it, and a listener reads a typed `e.detail` without a cast. Add a new cross-bundle event there, never as a string literal. Dispatch through `emitWindow()` or `emitDocument()`, never `new CustomEvent`, so tsc checks the detail and the target against the event's name. The `up:ready` and `up:notify` events are part of the README's public surface, so renaming either breaks sites.
- Sites' own scripts import `api.ts` as `unity/js/api`, so it is public surface too. Renaming or removing an export breaks sites, and `api.test.ts` lists the exports. Each site's bundle runs the top-level code of every module `api.ts` imports, so it imports only modules without side effects, such as `events.ts` and `types.ts`. The `api` site in `scripts/build-sites.ts` builds a site script that imports it.
- esbuild copies `desktop-select.ts` and `projects-desktop.ts` into both the app and projects bundles, so two instances coexist on the projects page. Keep all of their state inside the `createSelection` and `installDesktop` closures, and never add module-level mutable state to either file.

## Editing notes

- `app.ts` initializes the modules in a deliberate order, and its comments explain each dependency. Add new calls after the ones they depend on, wrapped in `run()` so one module's failure leaves the rest working. It dispatches `up:ready` on `document` last, which README.md documents for sites' own scripts.
- A new top-panel action is a name in `NAMED_ACTIONS` in `assets/unity/js/actions.ts`, a handler in the `ACTIONS` table in `top-panel.ts`, and a `data-action` row in `_partials/unity/top-panel/menus.html` or in one of the `_partials/unity/indicators/` partials. tsc fails until the names and the handlers match, and `actions.test.ts` fails on an action in the theme's layouts that `actions.ts` does not define. The Dash's app tiles name the same actions plus the Dash's own `trash` and `music:<index>`, and the HUD runs the panel's rows through the same handlers.
- tsc infers the result of `window.uiDialog` from the ids in a call's `buttons`. Comparing the result with an id the call does not pass fails to compile. Options typed as `UPDialogOptions` widen the result to `string`, so write the buttons in the call whenever the caller reads the result. `dialogs.test.ts` checks the inference.
- `shortcuts.ts` is a static table of bindings implemented elsewhere. Update it when a binding changes. Each row or section for a surface that a site can lack, such as the HUD or the solitaire table, takes a flag in `ShortcutSurfaces`. The dialog leaves out each one whose flag is false. The flag of a page that a site might lack comes from `UP_SITE`, because the dialog opens on every page.
- A new terminal command is a `shell/commands/*.ts` module appended to `ALL_COMMANDS` in `commands/all.ts`, which both the entrypoint and the test kit consume. Set `builtin: true` only for commands bash treats as builtins, because the flag decides whether `/usr/bin/<name>` exists.
- The shell core imports `terminal.ts` as a type only, so it runs headless. `shell/testkit.ts` runs the same programs through the shell and real bash and asserts they agree. Its `type()` delivers each argument as one input event, as xterm.js delivers a keypress or a paste, and `readline.test.ts` drives the line editor through it. Keep `vfs.ts` DOM-free and deterministic. Written nodes use the fixed `SESSION_MTIME`, and sizes derive from content, so golden `ls` output stays stable.
- The scripts under `scripts/` are TypeScript that Node runs directly, because Node 22.18 and later strip the types. Use only erasable syntax there. Node rejects enums, namespaces, and parameter properties at run time, and it does not resolve a relative import without its `.ts` extension. `npm run typecheck:node` checks the scripts and `vitest.config.ts` against `tsconfig.node.json`.
- Type every constant table as read-only, with `as const`, `readonly T[]`, `Readonly<T>`, or `ReadonlySet<T>`, so that no code can change what other code reads from it. Name a module-level constant in capitals and module state in camelCase. A getter for state that a setter guards returns the state read-only too, like `getParams()` in `audio.ts`. `readonly.test.ts` checks the type of each exported table, so add a new one there. It also scans every module. The scan fails when a capitalized const holds an array, object, Set, or Map literal without a read-only type.
- Tests are `*.test.ts` files under `assets/unity/js/`. Run them with `npm test` from this directory or from the site root. Helpers that several tests share live in a file named `testkit.ts`, which `tsconfig.test.json` checks and `tsconfig.json` leaves out. The tests of `main.css` read the stylesheet, its site tokens, its rules, and its declarations from `assets/unity/js/testkit.ts`. Every new test of `main.css` imports them from there and does not parse the file again. Every test that reads the theme's accent presets imports them from there as `accentPresets`, which smol-toml parses from `hugo.toml`.
- `npm run test:browser` builds the example site, serves it with the Content Security Policy that README.md documents, and loads every page in Chromium through Playwright. Each page must start the desktop without an uncaught exception or a console error. The console check fails on each module that `run()` in `app.ts` reports and on each inline style or script that the policy blocks. The specs live in `tests/browser/`, where Vitest does not look, and `npm run typecheck:test` checks them. Wait for a state through Playwright's polling assertions, never through a fixed delay. Run `npx playwright install chromium` once to download the browser.
- `npm run lint` runs Biome's recommended rules over the scripts. `biome.json` turns off three of them with a reason each: tsc's `noUncheckedIndexedAccess` makes a non-null assertion the honest way to state a proven invariant, the shell builds bash's `${...}` syntax in plain strings, and the ANSI parser matches control characters. Biome's formatter stays off, so the code keeps its hand-written layout.
- `biome.json` turns on `noFloatingPromises` and `useExhaustiveSwitchCases`, type-aware rules from Biome's nursery group. `noFloatingPromises` rejects a statement that drops a promise, so a call that leaves its promise unawaited on purpose starts with `void`. `useExhaustiveSwitchCases` rejects a switch that misses a member of the union it tests. Biome might change a nursery rule in any release, so `lint.test.ts` checks that each rule still fires. When a Biome upgrade moves either rule to a stable group, move its key in `biome.json`. `noUnnecessaryConditions` and `noMisusedPromises` stay off, because they flag correct checks of mutable class fields and of nullable promises.
